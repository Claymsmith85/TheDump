The short answer
Put it on the machine-wide module path with a manifest, and PowerShell will autoload it for every user on that device:


C:\Program Files\WindowsPowerShell\Modules\IdentityCheckout\
    IdentityCheckout.psd1
    IdentityCheckout.psm1
The folder name must match the module name. That path is on $env:PSModulePath for both Windows PowerShell 5.1 and PowerShell 7, so one copy serves both. Once it's there, Request-IdentityCheckout tab-completes and imports on first use in any user's session — no Import-Module needed.

Install steps (elevated, on the target device)

$dest = 'C:\Program Files\WindowsPowerShell\Modules\IdentityCheckout'
New-Item -ItemType Directory -Path $dest -Force | Out-Null
Copy-Item .\scripts\IdentityCheckout.psm1 -Destination $dest -Force
Unblock-File "$dest\IdentityCheckout.psm1"   # if copied from a share or download

New-ModuleManifest "$dest\IdentityCheckout.psd1" `
    -RootModule       'IdentityCheckout.psm1' `
    -ModuleVersion    '1.0.0' `
    -FunctionsToExport 'Request-IdentityCheckout','Connect-CheckedOutIdentity','Clear-IdentityCheckout' `
    -RequiredModules  'Az.Accounts','Az.Automation','Microsoft.Graph.Authentication'
The manifest matters: without it, command discovery depends on PowerShell parsing the .psm1, which is slower and less reliable. -FunctionsToExport mirrors the module's own Export-ModuleMember at scripts/IdentityCheckout.psm1.

Three things that will bite you
Signing is now mandatory, not optional. MANUAL-STEPS.md:118 already flags this. Under AllSigned or RemoteSigned, sign both the .psm1 and the .psd1 with a policy-trusted cert:


$cert = Get-ChildItem Cert:\LocalMachine\My -CodeSigningCert | Select-Object -First 1
Set-AuthenticodeSignature "$dest\IdentityCheckout.psm1" -Certificate $cert -TimestampServer 'http://timestamp.digicert.com'
Set-AuthenticodeSignature "$dest\IdentityCheckout.psd1" -Certificate $cert -TimestampServer 'http://timestamp.digicert.com'
Dependencies must also be AllUsers-scoped. Autoloading the module gets you nothing if Az.Accounts lives in one operator's CurrentUser scope:


Install-Module Az.Accounts, Az.Automation, Microsoft.Graph.Authentication -Scope AllUsers -Force
# plus, per service actually used:
Install-Module ExchangeOnlineManagement, MicrosoftTeams -Scope AllUsers -Force
-RequiredModules is a hard gate. If any listed module is missing, the import fails outright rather than degrading. If you'd rather operators get a clear error from the function itself, drop -RequiredModules from the manifest.

If you want it actually imported at session start
Autoloading covers the real goal. But if you need the module loaded before the first command — e.g. to print a banner about the checkout window — use the AllUsersAllHosts profile:

5.1: C:\Windows\System32\WindowsPowerShell\v1.0\profile.ps1
7: C:\Program Files\PowerShell\7\profile.ps1

Import-Module IdentityCheckout
Caveats: it's a separate file per PowerShell major version, it's skipped under -NoProfile, and the profile itself needs signing under AllSigned. Treat it as an addition to the module-path install, not a replacement.

The module's top-level Set-StrictMode -Version Latest and $ErrorActionPreference = 'Stop' stay module-scoped either way — they won't leak into operators' interactive sessions.

For fleet rollout
Everything above (copy → manifest → Unblock-File → sign → Install-Module -Scope AllUsers) is exactly what you'd wrap as an Intune PowerShell script or Win32 app scoped to the operator device group, with the code-signing cert deployed to LocalMachine\TrustedPublisher via a separate certificate profile.
